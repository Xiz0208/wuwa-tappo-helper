# Wuwa Tappo 助手

给桌面宠物 **Wuwa Tappo** 写的两件小工具，各自独立，用哪个就开哪个。

> 🤖 **先说清楚**：代码是 AI 写的，需求、测试和「这版不行，重做」是我干的。
> 具体分工见文末 [关于 AI](#关于-ai)。

| 模块 | 解决什么 | 入口 |
|---|---|---|
| **① 宝箱计时提醒** | 两个资源槽各自倒计时，攒满了提醒你一次，别白等也别忘领 | `启动宝箱计时器.bat` |
| **② 点数助手** | 人不在电脑前时补一点活跃度，让桌宠计数继续长 | `启动助手.bat` |

> 纯 PowerShell 5.1 + WinForms。零依赖、免安装、不写注册表（除了一个可选的开机自启项），
> 没有第三方库、没有编译产物。除推送功能外不联网，且只在提醒时发一次请求。

## 快速开始

1. 下载 Release 里的 zip，解压到**你自己可写的目录**（桌面、D 盘都行）
   ——别放 `C:\Program Files`，存档要写在文件夹里，只读目录存不下来
2. 双击 `启动宝箱计时器.bat`，第一次会弹出对表窗口，填上两个槽位当前剩余分钟（已满的填 0）
3. 需要刷点数就再双击 `启动助手.bat`
4. 想开机自动启动计时器：双击 `安装开机自启.bat`

不用了？托盘右键「退出」，再双击 `取消开机自启.bat`，系统里不留任何东西。

# 模块一 · 宝箱计时提醒

双击 `启动宝箱计时器.bat`。启动后不弹窗，直接待在托盘里。
托盘图标：双击 = 打开窗口；右键 = 连开两个 / 只开一个 / 对表 / 提醒设置 / 退出。

## 它解决什么问题

手动记倒计时的痛苦点不在于「算时间」，而在于：

- 两个槽位**各自**倒计时，长度不一样，脑子里同时维护两个数字很容易乱
- 到点了不一定有空去领，领了又忘了什么时候再满
- 满的时候不提醒你，你白等；提醒太频繁，又变成打扰
- 打游戏、看全屏视频时弹通知，直接把画面糊住

做法是：**只在「所有槽位都满」的那一刻提醒你一次，然后闭嘴。**

## 功能

### 槽位计时

- 两个槽位并行倒计时，互不干扰，所以两个数字长短不一样是正常的
- 槽位到点后停住并标记「已满」，等你处理；处理后才重新开始
- 大号数字显示剩余时间，进度条直观显示进度
- **对表**：直接输入实际剩余分钟数，立刻对齐，不需要知道偏差原因
- **撤销上一次** / `Ctrl+Alt+Z`：记错了原样还原，连对表都不用重做

### 提醒

- 两个槽位都满 → 提醒**一次**，之后不再重复打扰
- 系统提示音 + 托盘气泡 + 托盘图标变感叹号
- 可选推送到手机：企业微信群机器人 或 Server酱（见下方专章）
- **前台是全屏应用时，通知先攒着**，等你回到桌面再弹，不打断游戏/视频

### 定位式点击识别（推荐）

不想每次都按快捷键？可以把某个屏幕位置「标记」为操作点：

1. 点窗口里的「定位宝箱」→ 15 秒内把鼠标移到目标位置，点一下
2. 之后在那个点附近的快速点击会被自动识别为「已处理」，记时精确到秒
3. 点完不弹提示，界面上的数字立刻回到起点——看一眼就知道记上了

判定规则刻意写得很严，专防误记：

- 按下超过 600ms，或按下到松开位移超过 15px → 算拖动，不算点击
- 离标记点超过 80px → 不算
- 不在「两槽全满」状态下 → 一律不认（摆弄桌宠、开设置、手滑点到都不会被误记）
- 唯一的松口：两个都满时你开掉一个，**接下来 12 秒内还认**——因为第二个箱子通常是紧接着一起开的

### 全屏自动让位（附赠）

给「永远浮在最前面」的桌宠用，全屏时自动藏起来：

- 全屏游戏（独占 / 无边框）、播放器全屏、浏览器 F11 → 自动隐藏
- 回到桌面、或任何普通窗口（**包括最大化窗口**）→ 自动恢复
- 多显示器各按自己所在屏幕独立判断

# 模块二 · 点数助手

双击 `启动助手.bat`。带可视化窗口，关窗口 = 缩到托盘（不是退出）。
托盘图标双击 = 打开窗口；右键 = 显示 / 暂停 / 退出。

## 它做什么

以随机间隔向系统发送一个**没有副作用的虚拟按键**（F24），让 Wuwa Tappo 的键鼠计数增长。

F24 是个特殊选择：普通键盘上根本没有这个键，绝大多数软件也不响应它，所以不会触发任何实际功能。

**核心设计：只在你手离开键鼠时才发送。** 你一旦打字或点鼠标，助手立刻让路，绝不和你的输入抢时间，不会卡输入法。

节奏也不是机械节拍，而是模仿真人「打一串、停一下」：

| 参数 | 默认值 | 含义 |
|---|---|---|
| `$VirtualKey` | `0x87` | 发送的虚拟键（F24） |
| `$IdleGateMs` | `700` | 手停下多少毫秒后才开始发送 |
| `$BurstMinMs` / `$BurstMaxMs` | `40` / `120` | 连发时的间隔范围（毫秒） |
| `$RestChance` | `0.10` | 每按完一次，有这个概率进入停顿 |
| `$RestMinMs` / `$RestMaxMs` | `350` / `800` | 停顿长度范围（毫秒） |
| `$PauseOnGame` | `$true` | 下列进程在前台时自动暂停 |
| `$GameKeywords` | 见脚本 | 进程名关键词（`wuthering`、`kuro`、`launcher` 等） |

## 技术边界（重要）

这个模块的实现边界很清楚，写出来是为了让它可审查：

- 用 `GetLastInputInfo` 判断你是否在用键鼠，**不记录你按了什么键**
- 用 `SendInput` 发 F24，**不模拟鼠标点击、不发组合键、不操作任何窗口**
- **不联网、不读写任何文件、不碰游戏和桌宠的程序文件、不注入进程、不改内存**
- 前台命中 `$GameKeywords` 里的进程时**自动暂停**，不在游戏里添乱

它能做的只是「让系统认为有人在按键」。这个按键没有绑定任何功能，不会替你打怪、不会替你点按钮。

# 微信推送配置

箱子满了可以推到手机。点计时器的「提醒设置」，粘一个地址进去，点「测试」。**测试通过的会自动保存**（不用再点「保存」，免得测完忘了存）。

发不出去时，弹窗会直接显示服务端给的原因，比如 `code=40001 [AUTH]错误的Key` —— 那就是 SendKey 抄错了、少了字符或者带了空格。

## ⚠️ 先看这个：Server酱换过域名

如果你在网上搜到的是 `sc.ftqq.com`，**那个是 2023 年就停用的旧域名**，打不开是正常的，不是你的网络问题。

现在的正确地址是 **`https://sct.ftqq.com`**（多了一个 `t`）。

另外两个常见误会，先说清楚省得怀疑人生：

- **公众号不会回复你。** 关注「Server酱」公众号只是为了「收消息」，它不发验证码、不回复任何内容。配置全在网页上扫码完成
- **扫码不是在公众号里扫。** 是先在浏览器打开网页，再用微信扫网页上的二维码

## 方式一 · Server酱（个人微信就能收）

1. 电脑浏览器打开 **https://sct.ftqq.com**
2. 点「微信扫码登录」，手机微信扫一下并确认
3. 回到页面，点「直接生成 SendKey」
4. 复制那串 **`SCT` 开头**的字符
5. 拼成完整地址：`https://sctapi.ftqq.com/SCTxxxxxxxx.send`
   —— 把 `SCTxxxxxxxx` 整个换成你复制的 Key，**注意结尾的 `.send` 不要丢**
6. 粘进计时器的「提醒设置」→ 点「测试」
7. 微信收到「测试推送」就成了，会自动保存

免费额度每天 5 条。箱子满了一天最多提醒几次，够用。

## 方式二 · 企业微信群机器人（最省事，不依赖第三方网站）

1. 企业微信群 → 右上角 `…` → 群机器人 → 添加
2. 复制 Webhook 地址，形如：
   `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=xxxxxxxx`
3. 整条粘进「提醒设置」→ 点「测试」

（没有企业微信就用方式一）

## 方式三 · Server酱³（手机 App 版）

地址形如 `https://你的uid.push.ft07.com/send/你的key.send`，直接粘进去也行。

## 常见错误对照

| 现象 | 原因 |
|---|---|
| `code=40001` 错误的 Key | SendKey 抄错、少字符、带了空格，或用了别人的 Key |
| 提示 URL 不合法 / 无响应 | 少了 `https://`，或结尾 `.send` 丢了 |
| 测试成功但手机没收到 | 没在微信里关注「Server酱」公众号（不关注收不到） |
| 打不开 `sc.ftqq.com` | 旧域名已停用，改用 `sct.ftqq.com` |
| 给公众号发消息没反应 | 正常，它本来就不回复，配置在网页上完成 |

# 踩过的坑

这个项目大部分时间不是花在「写功能」上，而是花在下面这些地方。记下来，省得别人再踩一遍。

## 1. 怎么区分「真全屏」和「最大化窗口」

最直觉的做法是比较窗口矩形和屏幕矩形，相等就认为是全屏。**这个思路在任务栏设为「自动隐藏」时会全线崩溃**——
这时 `rcMonitor` 和 `rcWork` 完全相等，任何最大化窗口都会铺满整屏，于是浏览器最大化、文件夹最大化全被误判成全屏。

最终改成看窗口**样式**：

- 有 `WS_MAXIMIZE` 标志，且还保留标题栏 → 是最大化窗口，不算全屏
- 没有标题栏、没有可拖动边框 → 才是真全屏

这个判据稳定得多，因为「最大化保留标题栏、真全屏去掉所有窗口修饰」是 Win32 层面的语义区别，不会随任务栏设置变化。

## 2. 透明全屏层的位置读取

桌宠是一个**铺满屏幕的透明窗口**，角色在里面自由移动——
也就是说 `GetWindowRect` 永远返回整屏大小，从窗口位置完全看不出角色挪到哪了。

只能绕道去读它存进 WebView2 local storage 的角色坐标（形如 `{"x":{"ratio":1},"y":{"ratio":0.828}}`）。这里有两个坑：

- 那个 leveldb 文件在程序运行时是**被独占**的，普通读取会失败 → 必须用 `FileShare.ReadWrite` 打开
- 比例值只能算得出**相对位移**，如果两次采样中「贴边状态」变了（比如从贴右边缘拖到中间），横向位移就无解 → 此时不做猜测，直接提示用户重新定位

设计取舍：宁可提示「请重新标记」，也不去猜一个可能错 200 像素的坐标。

## 3. 「严格条件」反而导致漏记

最初把记录条件设成严格的「两个槽位都满」才认，逻辑上最干净。实际用起来发现：
用户开掉第一个箱子后，槽位立刻变成「倒计时中」，于是**紧接着开的第二个箱子永远记不上**。

修法不是放松条件，而是加一个**有时限的补偿窗口**：只有在「刚刚真的记过一次」之后，才开一个 12 秒的连开窗口；平时完全不生效。
这样既保住了「不在全满状态不乱记」的严格性，又覆盖了真实操作节奏。

## 4. 单实例与状态自愈

- 用命名互斥体 `Local\...` 防多开，第二个实例只弹一句提示就退出
- 存档里所有坐标记录**当时的分辨率**；分辨率变了就整块作废并提示重新定位，而不是拿旧坐标去点
- 开机自启项每次启动时比对一遍路径，不一致就重写（Windows 的自启项只认绝对路径，写不了相对路径，这是系统限制）

## 5. PowerShell + WinForms 的排版坑

- `AutoSize = $true` 的 `Label` 如果行高不够，文字会被**静默裁切**，不报错也不换行。多行说明必须手动定尺寸，或者逐行建独立 Label
- 透明 `Label` 的 Z 序如果不显式设置，会盖住相邻控件的绘制区域，看起来像「文字消失」
- 高 DPI 下建议统一用固定坐标 + 显式字号，别依赖自动布局

## 6. 推送接口的错误被异常吞掉

`Invoke-RestMethod` 在 4xx 时抛异常。如果只 `catch { "发送失败" }`，服务端返回的具体原因（错误码、错误描述）就丢了，
用户只会看到「发不出去」而无从下手。正确做法是从 `$_.ErrorDetails.Message` 里取出响应体，解析出 `code` 和 `message` 再展示。

# 设计取舍

几个刻意的「不做」，都是有原因的：

- **满了只提醒一次。** 反复弹窗在「你已经知道」之后就不再提供信息，只是噪音
- **不猜坐标。** 算不准的时候宁可让你重新标记一次，也不猜一个可能点错的位置
- **点数助手只在你离开时工作。** 会和输入抢时间的自动化工具，用起来是负担
- **不做成 exe。** 这类工具转 exe 极易被杀软误报，体积还从几十 KB 涨到几 MB。zip + bat 入口更透明，也更好审查

# 已知限制

- 极少数游戏用「最大化 + 保留标题栏」的方式做全屏，这种会被当成普通最大化窗口而不会触发自动让位。真遇到需要补规则
- 定位式点击识别依赖屏幕坐标，换显示器或改分辨率后需要重新标记（程序会自己发现并提示）
- 点击识别的前提是「那一下确实落到了目标窗口上」。如果有别的悬浮窗压在上面，点击会被那个窗口吃掉——程序会在诊断日志里写明是哪个程序，但无法替你穿透
- 推送依赖第三方服务，免费额度有限（Server酱每天 5 条），配额用尽时只保底本地提醒
- 点数助手的暂停名单是进程名关键词匹配，`launcher` 这类宽泛的词可能误命中一些启动器
- 截图 / 录屏工具（如 PixPin）的全屏工具栏可能被判成「真全屏」，导致桌宠短暂隐藏又恢复。实测中出现过，如果你常用这类工具，需要按进程名把它们加进排除名单

# 关于 AI

这个项目的代码几乎全部由 AI 生成。我一行都没背下来，所以别问我某个函数为什么这么写——问它。

我实际做的事只有三件：

1. **提需求** —— 「打游戏的时候它别挡着我」「两个槽位都满才提醒，别一直弹」
2. **当测试员** —— 一遍遍试：浏览器全屏藏不藏？文件夹最大化藏不藏？截图的时候它闪什么？
3. **否掉方案** —— 第一版是把桌宠压到最底层，结果它自己又弹回来，一闪一闪抢置顶。方案作废，重做。

所以：如果你觉得代码写得还行，功劳归 AI；如果你觉得某个设计很蠢，那大概率是我需求提歪了。

唯一能算我亲手完成的 KPI：把桌宠来回挪了几十次，验证坐标跟不跟得上。这个 AI 替不了，它没有手。
